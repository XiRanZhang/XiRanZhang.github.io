# 备份校验的线程号错配：把亚毫秒竞态变成确定性复现

> goInception PR [#720](https://github.com/hanchuanchuan/goInception/pull/720) · 2026 年 9 月提交 · 状态：**open，等待 review**
> 改动：5 个文件，+632 −2（其中 520 行是新增测试）· Fixes [#666](https://github.com/hanchuanchuan/goInception/issues/666)

上一篇复盘是一次 3 行的修复。这次相反：改动 632 行，其中 520 行是测试。因为**这次的难点不在改，而在"不确定"本身**——一个只在亚毫秒窗口里才会发生的错配，如果不能在测试里稳定复现，改对了也没人敢信。

## 现象：间歇性失败，且不留痕迹

开备份执行 DML 时，**间歇性**出现 `Backup failed`：

- SQL 实际执行成功，binlog 里确实有对应的行事件；
- 但备份校验没能生成回滚语句，语句被标记为失败；
- `error_message` **是空的**。

这个组合很反常。失败会失败，但**没有任何错误信息**意味着失败是"推断"出来的——某处有个计数没对上，代码据此判定备份没成功，却不认为这是个错误。

issue [#666](https://github.com/hanchuanchuan/goInception/issues/666) 的现象与之一致：go-mysql 日志确认收到了 `update_row` 事件包，但回滚语句没入库。报告者自己给出的方向恰好就是根因——**代理按语句断连，下一次查询拿到的 `connection_id` 变了**。

## 定位：线程号是从哪来的

顺着这条线索看备份校验的实现，链条是清楚的：

备份解析 binlog 时**按线程号过滤事件**（`parser.go` 的 `checkFilter` 要求事件线程号等于 `record.ThreadId`），只有解析到的变更行数 ≥ `AffectedRows`，记录才会从默认的 `StatusBackupFail` 翻成 `StatusBackupOK`。

所以 `record.ThreadId` 是**整个校验的锚点**——它必须精确等于"执行这条 DML 的那条连接的线程号"。那它是从哪来的？

```go
res, err = s.exec(sqlStmt, false)          // ① 语句在池连接 X 上执行
...
record.ThreadId = s.fetchThreadID()        // ② 另起一条池化查询「select connection_id()」
```

**① 和 ② 是两次独立的取连接操作。**

## 根因：身份取自另一条连接

`database/sql` 的连接池不保证连续两次操作落在同一条底层连接上。一旦池在 ①② 之间换连——坏连接被透明替换、代理按语句断连、池轮转——② 落在连接 Y 上，取回的是 Y 的线程号。

拿着 Y 的线程号去匹配连接 X 写出的 binlog 事件，**必然一无所获**：`changeRows = 0`，记录停在 `StatusBackupFail`，而这条路径不写任何错误信息。于是所有症状都能对上：语句成功了、binlog 有事件、回滚语句没生成、报错为空。

**这类 bug 的关键特征不是"取错了值"，而是"身份是从别处推断出来的"。** 线程号在语义上属于"执行语句的那条连接"，实现上却是从另一条连接上问来的——只要两者可能不同，锚点就是不可靠的。

窗口只有亚毫秒级，只有池恰好在此刻换连才触发，所以表现为间歇性、难以复现。

## 复现：把亚毫秒竞态变成构造保证

这是这个 PR 里我最有把握说"值得一看"的部分。

竞态类 bug 的常规做法是"跑很多次，看能不能撞上"，但那样得到的测试是概率性的，改完也不知道是真修好了还是运气好。要让人相信，需要**确定性等价物**——用构造保证复现出生产环境里靠运气才会出现的状态。

突破口是 `database/sql` 池的实现细节：取空闲连接取 `freeConn[last]`，归还时 append 到尾部——**LIFO**。既然顺序是确定的，就能安排出"必然取到哪条连接"的局面：

1. 把池内空闲连接**全部扣在池外**（用 `db.Conn` 循环取到 `Stats().Idle` 为 0）；
2. 执行 DML：此刻池内无空闲，语句**必然**落在一条新连接 X 上；把 `CONNECTION_ID()` 也写进表里，作为执行连接的 ground truth；
3. 归还一条被扣住的连接 A：按 LIFO，A 成为下次取连接的首选；
4. 旧实现的 `fetchThreadID()` **必然**落在 A 上——错配发生。

实测 `fetchThreadID = 5`，实际执行连接 `6`；同一场景下新实现是 `9 == 9`。

**为什么这是确定性的而不是"撞上的"：** 第 2 步执行期间 A 一直被扣在池外，A 在物理上不可能是执行连接。所以第 4 步的错配是构造保证的结果，不是竞态碰巧命中。这正是线上"间歇性"在测试里的确定性等价物——**把"某个窗口里可能发生"翻译成"这个窗口被我撑开了，它必然发生"**。

配套的四个用例：确定性复现（旧实现复现错配）、新实现一致性、端到端（`CONNECTION_ID()` 落库交叉验证 + `StatusBackupOK` + OPID）、`use` 切库后会话状态对齐。

## 修复：让执行与取号落在同一条连接上

```go
conn, err := db.Conn(ctx)     // 独占连接
defer conn.Close()

res, err = conn.ExecContext(ctx, sqlStr)
// 在同一条连接上取号，而不是再向连接池要一条
conn.QueryRowContext(ctx, "select connection_id();").Scan(&tid)
```

选 `*sql.Conn` 而不是"执行完再 `ping` 一下"之类的做法，是因为它的语义正好对上需求：**`database/sql` 保证用户持有的 `*sql.Conn` 在底层连接失效时返回错误，而不是静默换用别的连接。** 线程号与执行连接的一致性因此成为机制保证，而不是需要小心维护的约定。

三处细节是刻意的：

- **不做坏连接重试。** 与 `s.exec(retry=false)` 的语义保持一致：语句可能已经执行成功，此时重试就是重复提交。连接坏了就报错，让人工介入。
- **取号失败不返回错误。** 此时 DML 已经执行成功，把整个操作判为失败会让调用方误以为语句没生效。所以只记日志、返回 0，由调用方走兜底路径。
- **拿不到独占连接时退回原路径。** 兜底存在，但不再是常态路径。

## 同一个根因的第二副面孔

修完连接身份的问题后，我顺手查了同一类隐患，发现了另一个：

`USE 当前库`、`binlog_format=ROW`、`binlog_row_image=FULL`、`sql_safe_updates`、`lock_wait_timeout` 这些 `SET SESSION`，原本只通过 `s.exec` 设置在**池化连接**上。独占连接换了，它们同样会失效——`use` 切库之后不带库名前缀的 DML 会写错库，`binlog_row_image` 不是 FULL 会直接影响备份能否生成完整回滚语句。

根因和线程号错配是同一个：**"会话级状态"被默认绑定在"池化连接"上，但池化连接是会换的。** 于是新增 `alignSessionStateOnConn`，在独占连接上重新对齐这些变量，并用 `TestBackupDMLUseSwitch` 锁住。

**一个 bug 修完之后值得多问一句："同一类错误的第二个实例在哪？"** 这次的答案是"会话状态"，而且它的后果比错配更严重——错配导致备份失败，会话状态不一致可能导致备份成功但内容是错的。

## 顺带：不再静默失败

最初那个"`Backup failed` 且无错误信息"的形态，本身也是缺陷：失败被推断出来却不留证据，排查只能靠猜。`parser.go` 补上了具体信息：

```
备份校验未确认到全部变更行: 期望 N 行, 实际解析 M 行 (thread id: T)
```

**一个不解释自己的失败，会把定位成本从"读一行日志"抬到"重新推一遍调用链"。**

## 取舍

- **独占连接 vs. 复用池连接**：独占连接每次 DML 多一次取连接与对齐会话状态的开销。但备份 DML 不是高频路径，换来确定性的一致性，划算。
- **报错 vs. 兜底**：`database/sql` 的透明重连很"贴心"，但在这里恰好是毒药——它把"连接换了"这件事藏了起来。选择独占连接，等于主动放弃这层便利，换取"连接身份不会骗我"。
- **测试规模**：520 行测试远超 94 行实现。这不是比例失调——**竞态修复的可信度全部来自复现能力**，没有那个确定性构造，这个 PR 在 reviewer 眼里就只是"改了 94 行，看起来有道理"。

回归用 `go test ./session -run '^TestBackup$' -api` 在 docker mysql:5.7（ROW binlog）下跑，修复前后均为 200 passed / 20 环境相关 failed，**失败用例清单逐条一致**——零回归，而且是可比对的零回归。
