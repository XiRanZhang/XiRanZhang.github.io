# 有状态负载在 Kubernetes 上

这是一组技术文章的合集，主题只有一个：**有状态负载在共享 Kubernetes 集群上的放置、变更、隔离与弹性**。

每篇都从"问题与约束"写起：先看 Kubernetes 原生提供了什么、缺什么，再谈可行解法和它们的能力边界——**尤其是解法在哪儿失效**。

## 核心矛盾

Kubernetes 的调度与运维抽象是为无状态负载设计的：管理 Pod、节点和资源对象，用 readiness 探针判断"能不能用"，用 PDB 判断"一次能停几个"，用 reconciliation 收敛到期望状态。

数据库和分布式中间件不是这么工作的。它们维护的是**角色关系、成员集合和协议不变式**：谁是 primary、谁有投票权、成员集合是否满足 quorum、成员变更是否串行。这些概念在 Kubernetes 的对象模型里没有对应物。

于是出现这样的错位：每一个动作单独看都合规——"一次只重启一个 Pod"满足 PDB，"单个节点排空"满足驱逐条件——叠在一起却击穿了 quorum。问题不在某个参数配错了，而在于**控制面看不见底层系统的真实约束**。
